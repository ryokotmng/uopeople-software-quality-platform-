# Data Flow

Data moves through the platform along four distinct paths, one per capability, and all four are handled by the same process (`cmd/server`) rather than by separate services. At startup, `main.go` reads configuration from the environment (`config.Load`), opens the user store at `DATA_DIR/users.json`, opens the run store at `DATA_DIR/runs`, and passes both into `web.NewServer`, which wires them to a single `net/http` router. Everything below follows from that one wiring step: every request enters through the router and is dispatched to a handler that depends only on the service or store it needs, never on the others.

## Authentication flow

A client reaches `/login` in one of two ways: a browser requests `GET /login` and receives an HTML form, or a caller submits credentials to `POST /login` either as a browser form post or as a JSON body. Both submission paths converge on the same handler, which reads the username and password and calls `auth.Service.Valid`, which in turn calls `auth.Service.Authenticate`. That function looks the username up in an in-memory map that was loaded from `users.json` at startup, derives a PBKDF2-HMAC-SHA256 hash of the supplied password using the stored user's salt, and compares it to the stored hash in constant time. The result — authenticated or not — flows back up as a boolean, and the handler renders it as either an HTML confirmation/error page or a JSON body, depending on which path the request came in on. The credential store itself is only written to when a new user is registered (`Register` hashes the password, adds it to the in-memory map, and rewrites `users.json` in full via a write-then-rename); an authentication check never writes to disk, so `/login` reads are cheap relative to the deliberately expensive hashing computation. The same authentication function also guards `/api/runs/trigger`, but through HTTP Basic credentials on that endpoint instead of a posted form or JSON body.

## Reporting flow

`GET /report` is the simplest path in the system: the handler calls `reporting.GenerateReport` with a fixed, in-memory sample of test outcomes, which counts passed and failed entries and computes a pass rate, and serializes the returned struct directly as JSON. No disk access and no other module is involved, which is why this path is roughly three orders of magnitude faster than authentication.

## Test-orchestration and dashboard flow

This is the only path that writes application data, and it connects three layers end to end. An authenticated `POST /api/runs/trigger` request calls `orchestration.Run`, which shells out to `go test -json` against the configured repository, streams back newline-delimited JSON test events, and parses them into a single structured `RunResult` (counts plus any failure output). That result is hashed against nothing — it is handed directly to `store.RunStore.Save`, which serializes it to its own timestamped JSON file under `DATA_DIR/runs`, again using write-then-rename so a crash mid-write cannot corrupt a run record. From that point on, the run is durable and independent of the process that created it. The dashboard closes the loop on the read side: `GET /` calls `store.RunStore.List`, which reads every run file back off disk, decodes it, and sorts the results newest-first, and the handler feeds that slice into an `html/template` that renders the latest status, the failing-test log, and the run-history table. `GET /api/runs` exposes the same list as JSON for programmatic callers. Because the write side (`Run` → `Save`) and the read side (`List` → template) only share the file-based store and never call each other directly, either can be replaced independently — the design note in `docs/ci_dashboard_integration_design.md` describes swapping the store for PostgreSQL, or adding a second producer so GitHub Actions can post results into the same store over HTTP, without touching the orchestration or dashboard code.

## External measurement flow

Two flows sit outside the running server and exist purely to observe it rather than to change its data. `cmd/loadtest` opens real HTTP connections to a running instance and drives `/login` and `/report` with either sequential requests (to measure latency) or concurrent workers (to measure throughput); it never touches the server's internal state, only its public HTTP surface. GitHub Actions, triggered on every push, builds the binary, runs the full test suite (including the integration tests that exercise the flows above over `httptest.NewServer`), and separately builds the Docker image — a parallel, external flow that verifies the system rather than feeding data into it. Because CI results are not yet posted back into the run store, this flow terminates in the Actions log rather than in the dashboard; that gap, and how to close it, is what the CI-integration design document addresses.
